How to Monitor a URL for Changes (The Webhook Way)

Sep 2026 6 min read By snapwatch

Polling URLs is one of those tasks that looks simple — fetch, compare, repeat — until you're debugging why your cron job missed a change, or why your diff is full of noise from ad trackers and rotating timestamps. Here's the webhook-first approach that eliminates all of that.

Why polling is harder than it looks

A naive poller looks like five lines of code. The production version that actually works looks like 150+. Here's what the real complexity surface looks like once you try to monitor a URL for changes in earnest:

False positives from dynamic content. Most modern pages include timestamps, ad slots, session tokens, or A/B test identifiers that change on every load. A raw HTML hash will fire your alert on every single request, even when nothing meaningful changed.

Hash stability. To filter noise you need content normalization — stripping scripts, ads, and dynamic attributes before hashing. That's a non-trivial HTML parsing step, not a regex.

State storage. You need to persist the previous hash somewhere: a database, a file, a KV store. Add schema, migrations, or file locking depending on your stack.

Retry logic. The target URL returns a 429 or 503. Do you retry immediately? Exponentially? Do you skip the cycle or queue it? Each choice has edge cases.

Notification delivery. Once you detect a change, you need to deliver the alert reliably — email, Slack, webhook. That's another integration with its own failure modes.

The hidden cost: a "simple poller" that handles all of the above is a small microservice. You now own its uptime, its retries, its storage, and its notification pipeline. Most teams ship the naive version and wonder why it keeps misfiring.

The webhook-first approach sidesteps every one of these problems by moving them to infrastructure you don't have to maintain.

What webhook-first monitoring looks like

Instead of writing a poller, you register a watch via a REST call. The API takes ownership of everything that happens between "poll the URL" and "deliver the notification":

  • Scheduled fetching at your chosen interval
  • Content normalization and noise filtering
  • Hash comparison against the previous known state
  • Retry with backoff on network errors
  • Webhook delivery with structured JSON payload

Your application only needs to handle one thing: an incoming HTTP POST when something actually changed. That's the entire integration surface.

The complete integration surface you write javascript 
// This is the entire amount of code you maintain
app.post('/webhooks/snapwatch', (req, res) => {
  const { event, url, diff_summary } = req.body
  if (event === 'changed') {
    notifyTeam(url, diff_summary)
  }
  res.sendStatus(200)
})

Three ways to monitor a URL for changes

Not all URL monitoring approaches are equal. Here's an honest comparison of the three realistic options:

Approach Programmable Reliability Maintenance
DIY cron job Yes You own it High
Browser extension / SaaS GUI No Moderate None
REST API (snapwatch) Yes Managed None

DIY cron: Full control, but you own reliability, storage, and notifications. Works fine for one URL in development. Breaks under load or when the target flaps.

Browser extensions / SaaS GUI tools: Zero code, but zero programmability. You can't trigger downstream logic, log to your database, or integrate with your alerting stack. They notify a human, not a system.

REST API: You define the watch in code, changes arrive as structured webhook events, and your system responds programmatically. The right tool when URL monitoring is a component of a larger workflow.

Create a watch with cURL

Register a watch bash 
curl -X POST https://api.snapwatch.dev/v1/watches \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.com/pricing",
    "interval": "hourly",
    "webhook_url": "https://yourapp.com/webhooks/snapwatch"
  }'

The response includes a watch_id you can use to update or delete the watch later. Snapwatch begins polling immediately on creation.

Webhook handler with Express.js

webhook-handler.js javascript 
import express from 'express'

const app = express()
app.use(express.json())

app.post('/webhooks/snapwatch', async (req, res) => {
  // Acknowledge immediately — process async
  res.sendStatus(200)

  const { event, watch_id, url, detected_at, diff_summary } = req.body

  if (event === 'changed') {
    // diff_summary: { added_lines, removed_lines, changed_elements }
    await notifySlack({
      text: `Page changed: ${url}\n+${diff_summary.added_lines} / -${diff_summary.removed_lines} lines`,
    })

    await db.insert({
      watch_id, url, detected_at, diff_summary
    })
  }
})

app.listen(3000)

Tip: always respond 200 before doing async work. Snapwatch retries delivery if it doesn't receive an acknowledgement within 10 seconds — you don't want duplicate alerts from slow downstream calls.

Advanced: CSS selector targeting

Monitoring an entire page produces noise. Most of the time you care about a specific element — a price, a stock indicator, a release version string. Pass a selector field when creating the watch and snapwatch will scope its diff to that element only.

Scope the watch to a specific element javascript 
const res = await fetch('https://api.snapwatch.dev/v1/watches', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${process.env.SNAPWATCH_API_KEY}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    url: 'https://competitor.com/pricing',
    interval: 'hourly',
    webhook_url: 'https://yourapp.com/webhooks/snapwatch',
    // Only fire when this element changes
    selector: '.price',
  }),
})

Common selector use cases:

  • .price — competitor pricing pages
  • #stock-status — product availability monitors
  • .release-version — software release trackers
  • [data-status] — attribute-driven status indicators
  • .terms-body — legal document change monitoring

Selector-scoped watches are dramatically less noisy than full-page watches. On most e-commerce pages, limiting to .price reduces false positives to near zero.

Weekly digest: the weekly_digest event

Not every use case needs instant alerts. If you're running a broad monitoring operation — tracking dozens of competitor pages, for instance — a daily barrage of changed events is its own form of noise.

The weekly_digest event fires every Monday morning and summarises the past seven days of activity across all your watches. It's a single webhook call, not one per watch.

weekly_digest payload shape json 
{
  "event": "weekly_digest",
  "period": {
    "from": "2026-09-01T00:00:00Z",
    "to": "2026-09-07T23:59:59Z"
  },
  "summary": {
    "checks_run": 1344,
    "changes_found": 7,
    "watches_active": 8
  },
  "changes": [
    {
      "watch_id": "wch_abc123",
      "url": "https://competitor.com/pricing",
      "change_count": 3,
      "last_detected_at": "2026-09-04T14:22:00Z"
    }
  ]
}

Enable the digest by adding "digest": true to your watch creation payload. It coexists with real-time changed events — you can receive both, or only the digest if you prefer batch processing over instant alerts.

When to use digest mode: competitor intelligence workflows where you review changes weekly, compliance monitoring where a Monday morning report fits existing processes, or any case where you're monitoring more URLs than you can action in real time.
