Get a Webhook When a Page Changes: The Complete Guide

If your product needs to react when a specific web page changes — a competitor's pricing page, a public filing, a job listing, a product page — the cleanest solution is not a poller you manage. It's a webhook delivered to your endpoint the moment the change is detected.

1. The problem with polling for page changes

Building your own page-change poller sounds simple until you actually run one in production for a month. Here is what you will encounter:

  • Timestamp and ad noise. Nearly every modern page embeds the current timestamp somewhere — a "last updated" footer, an ad impression ID, an analytics beacon. A naive HTML diff sees a change on every single check, even when the content you care about did not move.
  • False negatives between polls. If you poll every 6 hours and a page changes and reverts within that window, you miss it entirely. The event happened; you never knew.
  • Storage overhead. To produce a useful diff you need to store the previous version. At scale — hundreds of URLs, retained history — this becomes an object-storage bill you did not budget for.
  • Brittle infrastructure. Headless Chromium instances crash. Proxies get blocked. CAPTCHAs appear. You end up maintaining what is essentially a scraping platform when you just wanted a simple notification.
  • No SLA. Your cron job has no retry logic. If it fails at 3am, you find out in the morning. The signal is gone.

The pattern that eliminates all of these problems is exactly how email, payment processing, and CI pipelines work: you register an endpoint, and the system calls you when something happens. That is a webhook.

2. How webhook-based page monitoring works

The model is straightforward:

1
You register a watch

You send a single API call with the target URL, a check interval, and your webhook endpoint URL. That is the entire setup.

2
The platform checks on schedule

A headless browser fetches the page on your chosen cadence — every 15 minutes, hourly, or daily. It handles JavaScript rendering, bot detection, proxy rotation, and content normalization automatically.

3
A diff is computed against the baseline

The platform computes a meaningful diff — stripping dynamic noise like timestamps and ad IDs — and compares the semantic content against the previous snapshot.

4
Your webhook fires

When a real change is detected, a POST request is sent to your endpoint with a structured JSON payload. Your server decides what to do next: send a Slack alert, update a database record, trigger a downstream workflow.

You own zero infrastructure. You write one HTTP handler. The rest is handled for you.

3. Setting up a watch: from zero to webhook in 5 minutes

Step 1 — Get your API key

Create a free account at snapwatch.dev. Your API key is on the dashboard under Settings → API Keys. It looks like sw_live_xxxxxxxxxxxxxxxx.

Step 2 — Register your watch with a single POST

You only need three fields: the URL to monitor, your webhook endpoint, and the check interval.

curl — create a watch
# Register a watch on a competitor pricing page
curl -X POST https://api.snapwatch.dev/v1/watches \
  -H "Authorization: Bearer sw_live_YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://competitor.com/pricing",
    "webhook_url": "https://yourapp.com/webhooks/snapwatch",
    "interval": "hourly",
    "label": "competitor-pricing"
  }'

The API responds with a watch object:

Response — 201 Created
{
  "id": "wch_2pKmR7xqNdBv",
  "url": "https://competitor.com/pricing",
  "webhook_url": "https://yourapp.com/webhooks/snapwatch",
  "interval": "hourly",
  "label": "competitor-pricing",
  "status": "active",
  "created_at": "2026-09-07T10:22:00Z"
}

That is it. Snapwatch will now check https://competitor.com/pricing every hour and POST to your endpoint if anything meaningful changes.

Step 3 — Handle the webhook with Express.js

On your server, all you need is a route that parses the JSON body and acts on it.

Node.js / Express — minimal webhook handler
import express from 'express'

const app = express()
app.use(express.json())

app.post('/webhooks/snapwatch', (req, res) => {
  const { event, watch_id, data } = req.body

  // Acknowledge immediately — Snapwatch will retry on non-2xx
  res.status(200).json({ received: true })

  // Handle asynchronously so you don't block the response
  handleEvent(event, watch_id, data).catch(console.error)
})

async function handleEvent(event, watchId, data) {
  if (event === 'changed') {
    console.log(`Change detected on watch ${watchId}:`, data.diff_summary)
    // your logic here
  }
}

app.listen(3000)
Always respond 200 before doing work. Snapwatch considers any response outside 2xx a failure and will retry. Acknowledge first, process in the background, so slow downstream calls like Slack or Notion never trigger a retry cascade.

4. The complete webhook payload

Snapwatch sends four event types. Every payload shares the same envelope structure — only the data field differs by event.

Event: changed

Fires when the page content differs meaningfully from the last snapshot. This is the event most integrations care about.

POST body — changed event
{
  "event": "changed",
  "watch_id": "wch_2pKmR7xqNdBv",
  "label": "competitor-pricing",
  "url": "https://competitor.com/pricing",
  "checked_at": "2026-09-07T11:00:03Z",
  "data": {
    "diff_summary": "Pro plan price changed from $49/mo to $59/mo. Enterprise tier removed.",
    "screenshot_url": "https://cdn.snapwatch.dev/screenshots/wch_2pKmR7xqNdBv/1725703203.png",
    "previous_screenshot_url": "https://cdn.snapwatch.dev/screenshots/wch_2pKmR7xqNdBv/1725699603.png",
    "change_score": 0.74,
    "sections_changed": ["pricing-table", "cta-section"]
  }
}

Event: blocked

Fires when the target page returns a CAPTCHA challenge, a 403, or a bot-detection wall that prevents a meaningful snapshot. Your watch stays active; Snapwatch will retry on the next interval.

POST body — blocked event
{
  "event": "blocked",
  "watch_id": "wch_2pKmR7xqNdBv",
  "label": "competitor-pricing",
  "url": "https://competitor.com/pricing",
  "checked_at": "2026-09-07T12:00:01Z",
  "data": {
    "reason": "captcha_detected",
    "http_status": 403,
    "message": "Cloudflare challenge page detected. Retrying next interval."
  }
}

Event: weekly_digest

Delivered once per week per watch. Useful for logging and audit trails even when no changes occurred, so you have proof the monitor is running.

POST body — weekly_digest event
{
  "event": "weekly_digest",
  "watch_id": "wch_2pKmR7xqNdBv",
  "label": "competitor-pricing",
  "url": "https://competitor.com/pricing",
  "checked_at": "2026-09-07T09:00:00Z",
  "data": {
    "period_start": "2026-08-31T09:00:00Z",
    "period_end": "2026-09-07T09:00:00Z",
    "checks_run": 168,
    "changes_found": 2,
    "blocked_checks": 0
  }
}

Event: error

Reserved for future use. When emitted, it will indicate a watch-level configuration error (e.g., an invalid URL that permanently fails). For now, treat it the same as blocked in your handler.

Field Type Present on Description
event string All One of changed, blocked, weekly_digest, error
watch_id string All Unique ID for the watch. Use this to route to the right handler.
label string All Human-readable label you set when creating the watch.
url string All The monitored URL.
checked_at ISO 8601 All UTC timestamp of the check that produced this event.
data.diff_summary string changed Plain-language summary of what changed.
data.screenshot_url string changed CDN URL of the latest screenshot. Valid for 30 days.
data.change_score float 0–1 changed Magnitude of the change. <0.1 is minor, >0.5 is significant.
data.checks_run integer weekly_digest Total checks performed in the period.
data.reason string blocked One of: captcha_detected, http_error, dns_failure, timeout.

5. Webhook reliability and retry logic

A webhook that fires once and gives up on failure is not a reliable signal — it is a best-effort notification. Snapwatch treats delivery as a first-class concern.

Retry schedule

If your endpoint returns a non-2xx status, or does not respond within 10 seconds, Snapwatch will retry with exponential backoff:

Attempt Delay after failure Total elapsed
1 (initial) — 0s
2 10 seconds ~10s
3 60 seconds ~70s
4 5 minutes ~6 min
5 (final) 30 minutes ~36 min

After 5 failed attempts, the event is marked as undelivered and logged in your dashboard. You can replay individual events from the dashboard or via POST /v1/events/{event_id}/replay.

Request headers

Every Snapwatch webhook request includes these headers, which you should use for routing and logging:

Header Value Use case
X-Snapwatch-Event changed, blocked, weekly_digest, error Fast routing without parsing body
X-Snapwatch-Watch-Id wch_xxxxxxxxxxxxxx Correlate event to a specific monitored URL
X-Snapwatch-Delivery-Id del_xxxxxxxxxxxxxx Idempotency — same delivery ID on retries
X-Snapwatch-Attempt 1, 2, 3… Log which attempt succeeded
Content-Type application/json Always JSON
Idempotency tip. Use X-Snapwatch-Delivery-Id as a deduplication key in your database. If a retry arrives after your first handler already succeeded, a quick lookup on this ID lets you skip processing and return 200 safely.

6. Security: verifying webhook authenticity

Any public webhook endpoint is, in theory, reachable by anyone. You should verify that a request actually came from Snapwatch before acting on it.

User-Agent identification

All Snapwatch requests include a consistent User-Agent header:

User-Agent: Snapwatch/1.0 (+https://snapwatch.dev)

This is useful for logging and basic filtering, but it is not a security mechanism — any client can set an arbitrary User-Agent.

Watch ID correlation (simple validation)

At minimum, check that the watch_id in the payload and the X-Snapwatch-Watch-Id header match a watch ID you actually created. If your handler receives a watch ID it does not recognize, discard the request.

Node.js — watch ID validation
const MY_WATCH_IDS = new Set([
  'wch_2pKmR7xqNdBv',
  'wch_9aXnQ4rTmCdL'
])

app.post('/webhooks/snapwatch', (req, res) => {
  const watchId = req.headers['x-snapwatch-watch-id']

  if (!MY_WATCH_IDS.has(watchId)) {
    return res.status(401).json({ error: 'Unknown watch ID' })
  }

  res.status(200).json({ received: true })
  // process...
})

IP allowlisting (strongest validation)

For production environments, allowlist the Snapwatch egress IP ranges. The current list is available at https://api.snapwatch.dev/v1/meta/egress-ips and is updated in real-time. At your load balancer or edge firewall, drop any request to your webhook path that does not originate from these ranges.

Do not rely on User-Agent alone. Combine at least two of: IP allowlisting, watch ID correlation, or a shared secret in the webhook URL path (e.g., /webhooks/snapwatch/sk_YOUR_SECRET_TOKEN). Defense in depth costs nothing here.

7. Real example: notify Slack when a competitor pricing page changes

This is the pattern most teams actually want. A competitor updates their pricing at 2am. You wake up to a Slack message with a plain-English summary and a screenshot link. Zero manual checking required.

Prerequisites: a Snapwatch API key, a Slack incoming webhook URL, and Node.js.

server.js — complete working integration
import express from 'express'

const app = express()
app.use(express.json())

const SLACK_WEBHOOK_URL = process.env.SLACK_WEBHOOK_URL
const SNAPWATCH_API_KEY = process.env.SNAPWATCH_API_KEY

// --- Register a watch on startup (idempotent in production) ---
async function ensureWatch() {
  const res = await fetch('https://api.snapwatch.dev/v1/watches', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${SNAPWATCH_API_KEY}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      url: 'https://competitor.com/pricing',
      webhook_url: 'https://yourapp.com/webhooks/snapwatch',
      interval: 'hourly',
      label: 'competitor-pricing'
    })
  })
  const watch = await res.json()
  console.log('Watch active:', watch.id)
}

// --- Post a rich Slack message ---
async function notifySlack(payload) {
  const { label, url, data } = payload

  const message = {
    blocks: [
      {
        type: 'header',
        text: {
          type: 'plain_text',
          text: `Page changed: ${label}`
        }
      },
      {
        type: 'section',
        fields: [
          { type: 'mrkdwn', text: `*URL*\n<${url}|${url}>` },
          { type: 'mrkdwn', text: `*Change score*\n${(data.change_score * 100).toFixed(0)}%` }
        ]
      },
      {
        type: 'section',
        text: {
          type: 'mrkdwn',
          text: `*What changed*\n${data.diff_summary}`
        }
      },
      {
        type: 'actions',
        elements: [
          {
            type: 'button',
            text: { type: 'plain_text', text: 'View screenshot' },
            url: data.screenshot_url,
            style: 'primary'
          },
          {
            type: 'button',
            text: { type: 'plain_text', text: 'Open page' },
            url: url
          }
        ]
      }
    ]
  }

  await fetch(SLACK_WEBHOOK_URL, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(message)
  })
}

// --- Webhook handler ---
app.post('/webhooks/snapwatch', (req, res) => {
  // Acknowledge immediately
  res.status(200).json({ received: true })

  const { event } = req.body

  if (event === 'changed') {
    notifySlack(req.body).catch(err =>
      console.error('Slack notification failed:', err)
    )
  }

  if (event === 'blocked') {
    console.warn('Watch blocked:', req.body.data.reason)
    // Optionally notify a #monitoring channel
  }
})

// Boot
ensureWatch()
  .then(() => app.listen(3000, () => console.log('Listening on :3000')))
  .catch(console.error)

Deploy this to any Node-capable platform — Railway, Fly.io, or a simple VPS — and you have a fully operational competitive intelligence feed with under 100 lines of code.

Production suggestion: Move the watch IDs into a database table rather than hardcoding them. This lets you add and remove watched URLs from an admin panel without redeploying. The Snapwatch REST API supports full CRUD on watches, so your UI can call it directly.
